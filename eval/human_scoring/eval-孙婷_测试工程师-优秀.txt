[候选人]
选择 Playwright 主要是为了应对电商场景里的 SPA 和异步渲染。Selenium 的隐式等待在动态表格和弹窗上经常超时或误判，而 Playwright 的 auto-wait 基于元素可操作状态，配合网络空闲等待，让用例稳定性大幅提升。当时 300+ 用例的失败率从 Selenium 初版的 12% 降到 3% 以内。

最有用的是多上下文（browser context）和路由拦截。秒杀下单流程需要模拟不同购物车状态，用 context 并行隔离，一台机器就能跑 8 个独立会话；路由拦截则可以 mock 第三方支付回调，不用每次真调外部接口。发现 15 个 P0 里，最典型的是一个订单状态轮询的竞态问题——前端在支付成功前会先更新本地状态，Playwright 的 trace viewer 录屏结合页面快照，直接抓到了 UI 跟接口返回不一致的瞬间。

另外，Playwright 的 network throttling 能模拟弱网，帮我们规避了超时类“假 Bug”，这比 Selenium 的 WebDriver 协议要高效得多。

[面试官]
你提到通过 trace viewer 抓到了"前端在支付成功前先更新本地状态"导致 UI 与接口返回不一致的竞态问题，能否具体说一下这个问题的根因是什么，以及你们最后是怎么修复的？

[候选人]
这个问题的根因是前端在支付接口返回前就乐观更新了本地状态，用“支付中”占位去渲染，导致 UI 与后端最终结果不一致。我在 trace viewer 里看到请求时序：点击支付后，前端立即 dispatch 了 `PAYMENT_SUCCESS`，而接口还在 pending；等接口返回失败时，已经来不及回滚，异常被吞了。

修复分两层：一是前端改为悲观更新，支付按钮触发后进入 loading 态，只根据后端响应驱动状态变更；二是后端加了幂等键和状态机校验，前端带着 `order_id` 重试时，服务端能识别重复请求并返回真实状态。另外我们在 E2E 里增加了网络延迟模拟，把这个竞态固化成回归用例，防止再次出现。整体上线后支付成功率从 98.9% 提升到 99.97%，误报 P0 清零。
